# AGENTS.md — Zunor

Канонічні інструкції для **будь-якого** coding-агента, що працює в цьому
репозиторії (Claude Code, Codex, Cursor тощо). Якщо створюєш `CLAUDE.md` —
роби з нього лише покажчик на цей файл, редагуй AGENTS.md.

## Про проєкт

**Zunor** — сервіс замовлення прибирання в Україні (старт з Одеси), задуманий
як agentic-альтернатива каталогам на кшталт Kabanchik: клієнт описує задачу
чат-асистенту платформи, а не шукає виконавця в списку. Окремого
персонажа-помічника («Zuna») в продукті більше немає — асистент говорить від
імені самого Zunor. Повний контекст
продукту, філософія і причини кожного рішення — у `MANIFESTO.md`. **Прочитай
його перед будь-якою продуктовою (не суто технічною) зміною** — там пояснено,
чому речі зроблені саме так, і є явний чек-лист «5 уникальностей», яким
звіряється кожне рішення.

**Цей репозиторій — тека `web/` у робочій теці `zunor/`**, поруч з іншими
проєктами, і в кожного свій git: `mobile/` (застосунок на Expo), `crm/`
(стара CRM), `backend/` (місце під майбутній API на Hono). Сайт і його API
живуть тут. Команди (`npm`, `npx prisma`, `git`) запускай усередині теки
проєкту, а не в корені. Карта робочої теки — `../AGENTS.md`.

Мова коментарів у коді — переважно українська (місцями російська), мова
самого коду (ідентифікатори, типи) — англійська. Дотримуйся цього балансу,
не перекладай існуючі коментарі без потреби.

### Тести

Vitest, конфіг — `vitest.config.ts`. Два проєкти в одному файлі, і плутати
їх не можна:

| Проєкт       | Оточення | `browser` | Що ганяє                           |
| ------------ | -------- | --------- | ---------------------------------- |
| `server`     | node     | `false`   | `src/tests/**`, крім `components/` |
| `components` | jsdom    | `true`    | `src/tests/components/**`          |

Обидва — **без плагіна `sveltekit()`**: повний пайплайн додав би залежність
від `.svelte-kit` і підняття dev-сервера на кожен прогін. Замість нього
віртуальні модулі (`$env/*`, `$app/*`) підмінені заглушками з
`src/tests/mocks`. Ганяти окремо — `npx vitest run --project server`.

**Усі тести лежать в одній теці — `src/tests/`**, поруч із кодом їх більше
немає. Ім'я файлу відповідає модулю, який він покриває, з префіксом теки,
якщо саме ім'я неоднозначне (`cleaning-validate.test.ts`,
`zunor-ai-profile.test.ts`). Імпорти — через `$lib/...`, не відносні.
`include` у конфізі звужений до `src/tests/**`, тож `*.test.ts` покладений
поруч із кодом просто не запуститься. Тека всередині `src/`, бо
`svelte-check` перевіряє саме `src/**` — у корені типи тестів ніхто б не
читав.

Покрите **чисте ядро** — модулі без БД, мережі й `$env`:
`server/dispatch/core/*` (бал, кільця, хвилі, рішення, рекомендації),
`geo/*`, `server/order-state-machine.ts`,
`categories/cleaning/validate.ts`, `categories/cleaning/effort.ts`
(обсяг заявки), `server/job-copy.ts`,
`server/zunor/detect-service.ts`, `server/zunor/chips.ts`, `server/user-dto.ts`,
`server/job-access.ts`, `orders/labels.ts`,
`zunor/dialog-storage.ts`, `components/chat/reactions.ts` і `linkify.ts`.

Окремо — **безпекові** тести на тому ж чистому ядрі: `utils/redirect.ts`
(open redirect), `username.ts` + `params/handle.ts` (підміна імені,
узгодженість із маршрутом), `server/rate-limit.ts` (ліміти й стеля
пам'яті), `server/zunor/ai-profile.ts` (prompt injection в анкеті),
`utils/json-ld.ts` (XSS у JSON-LD), `server/link-preview.ts` (SSRF:
приватні адреси, DNS, порти; DNS у тесті підмінений).

#### Серверні тести: `api/`, `loaders/`, `hooks.test.ts`

Роут у SvelteKit — звичайна функція `(event) => Response`, а лоадер —
`(event) => data`, тож і те, й інше тестується прямим викликом, без підняття
сервера й без БД.

| Тека             | Що покриває                                                          |
| ---------------- | -------------------------------------------------------------------- |
| `api/`           | усі 29 власних ендпоінтів (`api/auth/[...all]` — це сам better-auth) |
| `loaders/access` | сторінки з перевіркою доступу: заявка, замовлення, чат, профілі      |
| `loaders/guards` | лейаути, онбординг, налаштування, гарди за роллю                     |
| `loaders/lists`  | списки: дашборд, заявки, замовлення, сповіщення                      |
| `hooks.test.ts`  | порядок замків і заголовки безпеки                                   |

Харнес:

| Файл                     | Що дає                                                                            |
| ------------------------ | --------------------------------------------------------------------------------- |
| `helpers/event.ts`       | `makeEvent` (RequestEvent), `sessionUser`, `anonymous`, `failure`, `okJson`       |
| `helpers/prisma-mock.ts` | лінивий мок Prisma: `prisma.<model>.<method>` створюється на льоту                |
| `helpers/infra.ts`       | Pusher, Cloudinary, `Notify`, диспетчер, планувальник                             |
| `mocks/*.ts`             | заглушки `$env/*` і `$app/environment` (підключені аліасами у `vitest.config.ts`) |

Правила:

- **Жодних справжніх мереж і БД.** Що поверне база — задає сам тест
  (`prisma.job.findUnique.mockResolvedValue(...)`). Мок моделі повертає
  проміс за замовчуванням, бо справжня Prisma теж thenable.
- **Перевіряй ЩО поїхало в базу, а не лише статус.** Половина цінності цих
  тестів — у `prisma.job.findMany.mock.calls[0][0].where`: саме там видно,
  що фільтр не розширили з клієнта і що стеля на сторінку є.
- **Помилки роути кидають**, а не повертають: `error()` кидає
  `{ status, body }`, `redirect()` — `{ status, location }`. Для цього є
  `failure()`; він же падає з явним текстом, якщо роут раптом ПУСТИВ.
- **Імена подій Pusher звіряй із рядком-літералом** (`'message:new'`), а не
  з константою мока — інакше розсинхрон із фронтом пройде непоміченим.
- `rate-limit` тримає стан у пам'яті модуля, тож у тестах на ліміти кожен
  кейс бере **свій** `userId`.
- **Лоадер кидає `redirect()`, а не повертає його** — ловиться так само, як
  `error()`; у `loaders/*` для цього є локальний `redirectOf`.
- Якщо роут тягне барель із `.svelte` (наприклад `$lib/components/settings`),
  його треба замокати: без плагіна `sveltekit()` vite не розбере `.svelte`.
  Мокаємо саме барель, а не тягнемо в тести весь UI.

Секрети в `mocks/env-*.ts` фальшиві й лежать у репозиторії — справжніх туди
класти не можна ніколи.

#### Движок хвиль і AI-агент

Обидва покриті на тому ж харнесі, але з двома особливостями:

- **`dispatch-scheduler.test.ts` працює на фейкових таймерах** і
  `vi.setSystemTime`: хвилі рахуються від `createdAt`. Планувальник тримає
  стан у Map модуля, спільній на весь файл, тож `afterEach` обовʼязково

- **Правило стрічки перевіряється поведінково**: `dispatch-feed.test.ts`
  проганяє where через мінімальний обчислювач на справжніх заявках, а
  тести роутів шукають умови будь-де в where (`helpers/where.ts`), не
  прив'язуючись до вкладеності AND/OR.
- **`zunor-agent.test.ts` мокає `./deepseek`** і ганяє агента вигаданим
  виводом моделі. Перевіряється не «що сказала модель», а ПОСТОБРОБКА:
  чіпси, нормалізація Markdown, зріз передчасної пропозиції фото, валідація
  драфта, детект мови (видно через системний промпт у `mock.calls`).
  Стрім мокається асинхронним генератором, який повертає `StreamResult`.

#### Компонентні тести: `src/tests/components/`

Оточення jsdom, `@testing-library/svelte`, `browser: true`. Свій харнес:

| Файл                                 | Що дає                                                                                                             |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------ |
| `components/setup.ts`                | полифіли jsdom (`matchMedia`, спостерігачі, скрол, Web Animations, аудіо), гасіння переходів за `<a>`, `cleanup()` |

Правила:

- **Іконки не мокаються**: це наші крихітні `icons/set/*.svelte`, кожна

  Перевіряй підпис поруч, а не яка саме іконка намальована.
- **Стори — модульні синглтони**, спільні на весь файл тестів. `beforeEach`
  зобов'язаний їх скидати (`notifications.disconnect()`, `chatStore.setChats([])`),

- **Імена подій Pusher звіряй із рядком-літералом**, як і в серверних тестах:
  `handlerCount(CHANNEL, 'notification:new')`, а не константа з мока.
- **Компонент зі снипетами** приймає їх через `createRawSnippet`, окремі
  фікстур-`.svelte` для цього не потрібні.
- **Компонент із `setTimeout` тестуй на фейкових таймерах.** Не через
  швидкість: якщо компонент не знімає таймер при демонтуванні (як
  `username-input`), запит із попереднього тесту прилітає в наступний.

Покриті: обидва рунні стори (`notifications/store.svelte.ts`,
`stores/chat-store.svelte.ts`), `settings/*` (чотири картки в обох подачах +

картка сповіщень (`notifications/island.svelte` + `toast.ts`), `zunor/MessageBody`,
`chat/message-bubble` (реакції, посилання, цитата), чернетки чату (`chat/drafts.svelte.ts`),
`orders/order-card`, `dashboard/app-sidebar`, `profile/*`, `seo/JsonLd`,
`username-input`.

Панель дашборда (`dashboard-sidebar.test.ts`) вимагає власного батька —
`fixtures/sidebar-host.svelte`. Причина: `AppSidebar` читає контекст
`Sidebar.Provider` (стан «розгорнуто», `isMobile`, `toggle`), а той же

Підсунути це через опцію `context` не вийде — `setContext` працює лише
під час ініціалізації компонента, тож потрібен справжній батьківський
компонент. Перевіряється в ньому НАША логіка (склад пунктів за роллю,
підписи, активний рядок, бейджі зі сторів), а не розмітка бібліотеки.

**Що НЕ покрито** (щоб не шукати вдруге): `turn-log`-споживачі поза
`withTurnLog`, форми входу/реєстрації (`login-form`, `signup-form`,
`otp-form`), онбординг, чат цілком (`chat-window`, `message-composer`,
`chat-list-sidebar`), стрічки заявок (`master-feed`, `client-jobs`),
лендинг, завантажувачі фото і весь `components/ui/**` (це вендорений

`pusher.ts`, `mailer.ts`, `cloudinary.ts`, `auth.ts`, `deepseek.ts`)
юніт-тестів не потребують — вони лише конструюють клієнтів.

#### ⚠️ `\b` і `\w` у регексах — ASCII-only

Тут уже було дві діри одного кореня (детект мови й страховка фото-чіпсів у
`agent.ts` — обидві полагоджені). У JavaScript «слово» для `\b` і `\w` — це
`[A-Za-z0-9_]`, тому в суцільно кириличному рядку **межі слова немає ніде**,
а `\w*` завжди матчить порожній рядок. Регекс виглядає робочим, мовчки не
спрацьовує ЖОДНОГО разу, і помітити це можна лише тестом.

Пишеш регекс по українському чи російському тексту — бери Unicode-класи:

```ts
/(?<![\p{L}\p{N}_])(привіт|треба)(?![\p{L}\p{N}_])/giu  // замість \b…\b
/(додат|добав)\p{L}*\s+фото/iu                         // замість \w*
```

Так зроблено в `agent.ts`: межі слова там будує хелпер `marker()`, а не
`\b`. Прапорець `u` обовʼязковий — без нього `\p{L}` це просто літера «p».

Тестуй **поведінку, а не числа**: у scoring перевіряється «новачок обходить
рівного ветерана», а не конкретний бал — константи в `DISPATCH_CONFIG`
крутити можна, обіцянки з `MANIFESTO.md` ні.

Важливо: `npm run check` НЕ ловить зайві поля у вкладеному relation-`select`
Prisma 7 — такий запит проходить типізацію і падає лише в рантаймі. Якщо
міняєш поля моделі, перевіряй усі `select` грепом, на типи не покладайся.

### Prisma

Клієнт генерується **не** в `node_modules`, а в `src/generated/prisma`
(див. `generator client` у `prisma/schema.prisma`). Імпортувати звідти:

```ts
import { PrismaClient } from '../../generated/prisma/client' // з src/lib/server/*
import type { Role, OrderStatus } from '../../generated/prisma/client'
```

Після будь-якої зміни `schema.prisma` — прогнати міграцію
(`npx prisma migrate dev`), не редагувати `prisma/migrations/*` вручну.

**RLS увімкнений на всіх таблицях `public`** (міграція
`20261102120000_enable_rls`), без політик і без `FORCE`. Застосунок його не
помічає: Prisma ходить роллю-власником таблиць, а власник RLS обходить.
Закрито все для будь-якої іншої ролі (Neon Data API, окремий користувач
для аналітики). Звідси три правила:

- **Нова модель — `ENABLE ROW LEVEL SECURITY` у тій самій міграції.**
  Prisma про RLS не знає й сама його не допише: створи міграцію з
  `--create-only`, додай у кінець
  `ALTER TABLE "NewTable" ENABLE ROW LEVEL SECURITY;` і лише тоді застосуй.
- **Ніколи `FORCE ROW LEVEL SECURITY`** — без політик Prisma отримувала б
  порожні списки й падала б на записі.
- **`DATABASE_URL` — лише роль-власник.** Підключити застосунок окремою
  роллю (`app_user`) — те саме, що `FORCE`: база для нього порожня.

## Аліаси шляхів

SvelteKit-стандартний `$lib` → `src/lib`. Додатково, за `components.json`,
використовуються ці підаліаси (усі теж усередині `$lib`):

```
$lib/components  → компоненти
$lib/components/ui → shadcn-svelte UI-кіт
$lib/utils       → утиліти
$lib/hooks       → хуки
```

Використовуй `$lib/...`, не відносні `../../../` для всього, що виходить за
межі сусідньої теки.

## Ключові архітектурні патерни

### 1. «Движок vs контент» (з `MANIFESTO.md`, розділ 4)

При кожній технічній зміні став собі питання: **це движок чи контент?**

- **Схема БД, API-ендпоінти** — мають лишатися універсальними. Не додавай
  колонок/полів на кшталт `windowsCount` в `Job.metadata`-модель — усе
  специфічне для категорії живе в `metadata: Json?`.
- **Wizard-форми, тексти, іконки, термінологія** («клінер», «прибирання») —
  навмисно захардкожені під прибирання, зосереджені в окремих файлах
  (`src/lib/categories/cleaning/`, `src/lib/orders/labels.ts`).
- Мета: додавання нової категорії послуг завтра — це додавання контенту
  (нова тека в `categories/`, запис у `categories/registry.ts`), а не
  переписування движка.
- Те саме з містами: райони з координатами — таблиця `District`, привʼязана
  до `City` (як і самі міста, наповнюється сідом: дані в
  `prisma/data/districts.ts`, запуск `npx tsx prisma/seed-districts.ts`).
  Місто без районів у БД працює без кілець, район не питається.

**Не роби:** generic-wizard з конфігом із БД, мікросервіси, абстракції «про
запас» — проєкт свідомо лишається монолітом на SvelteKit.

### 2. Guard-и авторизації — два різних інструменти, не плутати

- **`src/lib/server/guard.ts` → `requireRole(locals, allowed, redirectTo)`** —
  для `+page.server.ts` / `load()`, коли треба перевірити **роль з БД**
  (роль читається напряму з таблиці `User`, не з сесії — сесію клієнт
  теоретично контролює, БД ні). Викликається одним рядком на початку `load`.
  На `/dashboard/**` бере готову роль з `locals.account` (її вже прочитав
  `guardHandle`), тож зайвого SELECT не робить.
- **`src/lib/server/guards.ts` → `requireUser` / `requireApiUser` /
  `requireApiSession`** — робота з `locals` (уже резолвлена сесія з
  `hooks.server.ts`). `requireUser` редіректить сторінку на логін,
  `requireApiUser`/`requireApiSession` кидають **401**, бо API-клієнту
  потрібен статус-код, а не HTML-редірект.

**Ніколи не викликай `auth.api.getSession()` у роуті.** Сесію на кожен запит
резолвить `sessionHandle` один раз і кладе в `locals` — повторний виклик це
зайва робота на кожен запит. Виняток лише один: `hooks.server.ts` (де вона й
резолвиться) та `api/auth/[...all]`, який віддає сам better-auth. Кілька
ендпоінтів (`upload/signature`, `user/media`, `user/update`) віддають 401 у
власному форматі `{ error }` замість `{ message }` від `error()` — там сесія
береться з `locals` напряму, без гарда, щоб не міняти контракт відповіді.

Не імплементуй перевірку сесії/ролі власноруч у роуті — завжди через ці
хелпери, інакше повторюється баг, описаний прямо в коментарі `guard.ts`
(сторінка майстра тихо показувалась клієнту).

### 2.1. Деплой: один довгоживучий Node-процес

Адаптер — `@sveltejs/adapter-node` (Hostinger Business Web Hosting), а не
serverless. Практичні наслідки, на які спирається код:

- Стан у пам'яті процесу **працює**: `rate-limit.ts`, `presence.ts`,
  `account-cache.ts`, `dispatch/scheduler.ts`. Redis не потрібен.
- `setTimeout` переживає між запитами — на цьому тримається планувальник
  хвиль (розділ 5).
- Ціна: перезапуск процесу обнуляє лічильники лімітів і скасовує
  заплановані хвилі. Перше прийнятне, друге підхоплює відновлення розсилки
  на старті процесу (`init` у `hooks.server.ts`): номер відпрацьованої
  хвилі лежить у заявці (`Job.dispatchWave`), а не в пам'яті.

Якщо колись з'явиться другий інстанс — усе перелічене доведеться виносити
в спільне сховище. Тоді Upstash (HTTP), а не класичний Redis по TCP.

**Другий спосіб — Vercel** (функції; покроково — `docs/deploy-vercel.md`).
Адаптер обирає `svelte.config.js` за `VERCEL=1`, режим у коді —
`serverless` з `$lib/server/runtime`. Копій функції кілька, кожна зі своєю
памʼяттю, а між запитами її можуть заморозити. Тому там:

- **хвилі 2–4 і повтори — черга Upstash QStash** (`dispatch/queue.ts`,
  виклик `POST /api/dispatch/wave` з підписом), а не `setTimeout`;
  `cancelWaves` там нічого не скасовує — хвиля закритої заявки сама
  відповідає «стоп»;
- **ліміти** (`rate-limit.ts`, ліміти better-auth) і **код 2FA адмінки**
  (`admin/step-up.ts`) — у Redis; стан акаунта — лише Redis, без памʼяті
  процесу; кеш чату Telegram — 30 с. Redis на Vercel обовʼязковий;
- **нагадування, прострочені заявки й відновлення розсилки — крон Vercel**
  (`vercel.json`, раз на добу); `init` там не ставить таймерів і не
  відновлює розсилку, а вебхук Telegram ставить лише бойовий деплой
  (`productionDeploy`), не прев'ю;
- **робота після відповіді — лише через `background()`**
  (`$lib/server/background`, `waitUntil`): голий `void проміс` на Vercel
  обривається разом із функцією — так губились би листи з кодом.

Нове місце зі станом у памʼяті чи з таймером — одразу думай, що буде на
Vercel: або спільне сховище, або гілка `serverless`.

Оскільки процес один, будь-яка структура в пам'яті мусить мати **стелю**:
`rate-limit.ts`, `presence.ts`, `account-cache.ts` обмежують свої Map явно.
Мапа без стелі, ключ якої залежить від чогось під контролем клієнта, —
це не витік пам'яті, а спосіб покласти весь застосунок одним скриптом.

### 2.2. Безпека: правила, які не можна порушувати

- **Перевірка доступу живе в одному місці, а не в кожному роуті.** Заявку
  віддають і сторінка, і `GET /api/jobs/[id]` (застосунок) — правило для
  обох у `$lib/server/job-access.ts`, а самі дані (пропозиції, «чи може
  майстер відгукнутись», перегляд і «майстер відкрив» для розсилки) —
  `$lib/server/job-detail.ts`, один завантажувач на обох. Коли воно було лише на сторінці, ендпоінт
  роками віддавав чужі заявки разом із фото помешкання клієнта. Додаєш
  третій шлях до тих самих даних — клич ту саму функцію.
- **Чужий об'єкт — 404, а не 403.** 403 підтверджує, що запис існує, і
  дозволяє перебором зібрати карту бази. 404 не каже нічого.
- **Ніякого `JSON.stringify` у `{@html}`.** Для JSON-LD є
  `$lib/utils/json-ld` (`safeJsonLd`) — він екранує `<`, інакше ім'я
  майстра з `</script>` стає stored XSS на публічній сторінці. Інших
  `{@html}` у проєкті бути не повинно.
- **Масив із тіла запиту завжди має стелю** перед тим, як піти в
  `{ in: [...] }`. Без неї один запит перетворюється на IN-список
  довільної довжини.
- **Не лімітуй за `X-Forwarded-For` вручну.** Лівий елемент заголовка
  задає клієнт: це і обхід ліміту, і накачування пам'яті. Потрібен IP —
  бери `event.getClientAddress()` (adapter-node рахує його за
  `ADDRESS_HEADER`/`XFF_DEPTH`).
- **URL від клієнта не пишемо в базу як є.** `api/user/media` приймає
  посилання на аватар/портфоліо тільки з `res.cloudinary.com`, тільки з
  **нашої хмари** (перший сегмент шляху дорівнює `CLOUDINARY_CLOUD_NAME`) і
  тільки таке, що містить перевірений `publicId`. Без перевірки хмари
  підходило б посилання на чужий Cloudinary-акаунт зі своїм `publicId` у
  шляху — тобто картинку можна було б підмінити ПІСЛЯ модерації.
- **За адресою від користувача сервер ходить лише через
  `$lib/server/link-preview`.** Там SSRF закрита повністю: лише http(s) і
  стандартні порти, адреса перевіряється ПІСЛЯ DNS у `lookup` самого
  підключення (окрема перевірка імені обходиться DNS-rebinding'ом, а
  `localtest.me` резолвиться в 127.0.0.1), редіректи — вручну з
  перевіркою кожного кроку, без пулу зʼєднань, тайм-аут і стеля на
  розмір після розпакування. Новий `fetch` за адресою з тексту чи
  профілю в обхід цього модуля — це доступ до localhost і метаданих
  хмари для будь-кого з акаунтом.
- **Числа з query — через `$lib/server/query`** (`intParam`, `moneyParam`).
  `Number('abc')` це `NaN`, а `Math.min`/`Math.max` його не виправляють, а
  ПРОПУСКАЮТЬ: `take: NaN` доїжджав до Prisma й перетворювався на 500.
  `?limit=abc` клав ендпоінт будь-кому без сесії.
- **`redirectTo` чистимо від керуючих символів ДО перевірки** і віддаємо
  вже вичищений рядок (`$lib/utils/redirect`). Браузер викидає `\t`, `\n`,
  `\r` з URL сам, тому `/<TAB>/evil.com` ставало `//evil.com` — чужий домен
  із живою сесією. Перевіряти треба те, що ПОБАЧИТЬ браузер, а не сирий
  рядок.
- **`onboarded` і `role` не приймаються з тіла запиту.** Їх пише лише
  `$lib/server/profile.ts` після повної валідації: `{"onboarded": true}`
  відмикав дашборд із порожнім профілем, обходячи замок №3 у
  `hooks.server.ts` одним запитом із DevTools.
- **Видалення акаунта — знеособлення, а не DELETE рядка User**
  (`$lib/server/account-deletion`, `DELETE /api/me`, кнопка в
  «Налаштування → Безпека» з підтвердженням своєю поштою). На
  користувача посилаються замовлення, повідомлення й відгуки ДРУГОЇ
  сторони, тож рядок лишається як «Видалений акаунт» (`DELETED_NAME`):
  стираються імʼя, пошта (службова `deleted-<id>@deleted.invalid`), handle,
  телефон, фото, анкети, способи входу, сесії, сповіщення, коди; файли —
  уся тека `zunor/users/<id>/` у Cloudinary. Відкриті заявки скасовуються
  (з `cancelWaves`), пропозиції відкликаються, `masterProfile.isActive =
  false` прибирає з розсилки, стрічки й рекомендацій; `banned` — друга
  лінія проти живої сесії з cookie-кешу. З активним замовленням — 409.
  Нове поле з персональними даними в `User`/`MasterProfile` — допиши його
  стирання туди ж, інакше воно переживе видалення.
- **Телефон — після угоди.** Він з'являється в `select` лише там, де вже
  є `Order` і перевірено, що глядач — його учасник (див.
  `dashboard/orders/[id]`). У стрічці, на сторінці заявки, у профілі
  клієнта його немає навмисно.

### 3. `hooks.server.ts` — порядок middleware критичний

Ланцюжок: `securityHeaders → authHandle (better-auth) → sessionHandle
(locals.session/user) → guardHandle (banned → emailVerified → onboarded →
маршрут)`. Єдине джерело правди про сесію на запит — `locals`, не читай
сесію повторно всередині окремих роутів.

### 4. Order state machine

Усі переходи статусу `Order` (`CREATED → IN_PROGRESS → COMPLETED`, або
`CANCELLED` з обох) описані централізовано в
`src/lib/server/order-state-machine.ts` через `canTransition()` /
`nextStatus()`. **Не міняй `order.status` напряму в Prisma-запиті** з
роуту — завжди через цю стейт-машину, вона ж перевіряє, хто (`CLIENT` /
`MASTER` / `SYSTEM`) має право на перехід.

### 5. Мозок підбору майстрів (`src/lib/server/dispatch/`)

Серце продукту: кого з майстрів кликати на заявку й коли (хвилі-кільця від
району заявки), що майстер бачить у стрічці і кого першим бачить клієнт.
Реалізує «push, а не pull» і «справедливий маркетплейс» з `MANIFESTO.md` —
зміни звіряй з «Уникальністю №2 і №5» та розділом «Районы и кольца
рассылки».

**Будова, потік і обіцянки — у `src/lib/server/dispatch/README.md`.** Тут —
лише правила для того, хто його чіпає:

- **Роути імпортують тільки з `$lib/server/dispatch`** (`index.ts`). Тести
  мокають саме барель (`helpers/infra.ts`); підмодулі напряму — лише в
  юніт-тестах самого мозку.
- **`core/` — чисті функції**: жодної БД, мережі й `new Date()` всередині
  (`now` передається). Логіка — там, читання й запис — у `data/`.
- **Усі числа — у `config.ts`.** Окремої копії порогу в роуті бути не
  повинно.
- **Ваги одні для розсилки й рекомендацій** (`core/score.ts`,
  `masterScore`): міняєш вагу — вона міняється і для клієнта.
- **Стрічка майстра — лише через `masterFeedScope`**, і для SSR
  (`dashboard/jobs`), і для догрузки (`api/jobs/feed`).
- **«Топ для тебе» — лише через `bestMatches`** (`dispatch/fit.ts`,
  рішення — `core/fit.ts`), у тих самих двох місцях. Правило — «розсилка
  покликала б першою хвилею й без штрафу»: перше кільце в часі дороги,
  `crewFit ≥ 0`, авто, якщо треба вивезти. Окремої формули чи ваг для
  стрічки немає — складові ті самі, що в `score.ts`. Не більше
  `BEST_MATCH_LIMIT` карток на сторінку.
- **Новий шлях, яким заявка перестає приймати відгуки, — `cancelWaves`**
  (зараз: `DELETE /api/jobs/[id]` і `POST /api/proposals/[id]/accept`).
- **Новий шлях, яким заявка (знову) відкривається, — `startWaves`**
  (зараз: `POST /api/jobs` і відмова майстра в `api/orders/[id]/[action]`).
  `dispatchJob` назовні не віддається: лише `startWaves` має повтори.
- **Покликаний без сповіщення неможливий.** `NEW_JOB` пишеться в
  транзакції хвилі разом із журналом (`recordWave`), а подія Pusher — після
  коміту (`pushNotification`). Окремого `Notify.newJob` немає навмисно.
- **Межа майстра — не абсолют.** Кільця її тримають; остання хвиля кличе
  й тих, кому далеко, якщо заявку побачило менше `LAST_CALL_MIN_REACH`
  майстрів. Тому стрічка показує покликаному його заявку завжди.

Райони, з яких рахуються кільця:

- **Відстань рахується в памʼяті** (`$lib/geo`), а не в БД. Райони живуть у
  таблиці `District`, але читаються лише через `getDistricts()` із кешу
  довідників (`reference.ts`): розсилка питає їх на кожну хвилю.
- `$lib/geo/districts.ts` — чисті функції над СПИСКОМ районів одного міста
  (`cityDistricts`). Райони різних міст не порівнюються: slug `center` може
  бути в обох, тому відстань майстра з чужого міста — null.
- У тестах мокається `getDistricts` (`helpers/districts.ts`), а не
  `prisma.district`: кеш модуля пережив би `resetPrisma()`.
- **Район заявки — з профілю клієнта на сервері**, не з тіла запиту.
- `slug` району — ключ у БД (`User.district`, `Job.district`). Назву міняти
  можна, slug — ні.

Анкета майстра (які прибирання, де, авто, формат роботи) й обсяг заявки:

- **Спільне для всіх категорій — колонки, вміння — `metadata`.** Авто й
  формат роботи — `MasterProfile.hasVehicle`, `crew` (enum `CrewType`:
  SOLO / TEAM / COMPANY). Уміння всередині категорії —
  `MasterProfile.metadata.skills[slug]`, це контент
  (`categories/cleaning/skills.ts`). Пише все лише `saveMasterProfile`, і
  відповіді обовʼязкові: «не відповів» означало б «отримуй усе підряд».
  У JSON `vehicle`/`team` більше немає — міграція
  `20261029120000_master_crew_job_effort` перенесла їх у колонки.
- **Людина чи компанія — перше питання анкети, а не окреме поле.**
  Компанія — це `crew = COMPANY` (`kindOfCrew` у `$lib/masters/meta`), і
  від відповіді залежить решта анкети: назва замість імені, логотип
  замість фото, «сам чи з напарником» компанію не питаємо. **Назва
  компанії — це `User.name`**, як імʼя в людини: його показують усюди, де
  видно майстра (профіль, пропозиції, чат, відгуки), тож окремої колонки
  немає — дві назви рано чи пізно розійшлись би (колонку `companyName`
  прибрала міграція `20261029180000_company_name_in_user_name`). Форма
  тримає імʼя й назву окремими чернетками: інакше імʼя з Google-акаунта
  ставало б «назвою компанії».
- **Обсяг заявки `Job.effort` (1–10) рахує сервер, а не модель.** Формула
  — контент категорії (`categories/cleaning/effort.ts`: години роботи
  однієї людини з полів заявки), шкала й рівні — `$lib/categories/effort`.
  Асистент дає лише поправку `effortAdjust` ±1 за тим, чого немає в полях
  («вітрини в ТЦ»): бал від моделі плаває від запуску до запуску, а
  поправка йде через браузер клієнта (чернетка → `POST /api/jobs`), тож
  більший крок дозволив би переписати бал руками. З названою площею −1
  не діє: модель ставила його «лише кухні» поверх 10 м², і малий розмір
  рахувався двічі (заборона в промпті цього не прибрала). У базі — CHECK 1–10.
  Заявка старша за поле (`effort = null`) — розсилка рахує обсяг із
  `metadata` тією ж формулою.
- **Формат × обсяг — мʼяко, через чергу** (`crewFit` у `core/score.ts`,
  ваги `CREW_FIT`): на дуже велике першими компанії й бригади, на
  невелике — ті, хто працює сам. Нікого не відсіює: заявку бачать усі, кому
  вона підходить.
- **Движок питає категорію, а не знає про прибирання.** Умови на
  `Job.metadata`, «потрібне авто», обсяг — `$lib/categories/matching`
  (`matchingFor`). Нова категорія без запису там підходить усім і обсягу
  не має (`effort: null` → формат роботи не впливає).
- **Той самий відсів у трьох місцях:** розсилка (`loadCandidates`),
  стрічка (`masterFeedScope` → `skillsWhere`, обидва виклики передають
  `categories` і `masterMeta` — це `MasterProfile.metadata`) і
  рекомендації (`recommendForJob`: `hasVehicle`, `crew` майстра й
  `effort` заявки). Додаєш четвертий шлях до заявок майстра — передай те
  саме.
- **`null` у відповіді — «не відповідав», не «ні».** Старий профіль не
  отримує ні переваги, ні відсіву; відсіює лише явне `hasVehicle: false`.

### 5.1. Розклад крона і чому він рідкісний

`/api/cron` — **страховка**, а не основний механізм. Хвилі ведуть таймери
й повтори в памʼяті, а загублене ними підхоплює `resumeDispatch` на старті
процесу. `dispatch-waves` кличе те саме відновлення — на випадок, коли
процес жив, а хвиля вичерпала повтори (база довго лежала).

```
dispatch-waves — раз на 30 хвилин
auto-expire    — раз на добу
reminders      — раз на добу, о 18:05 за Києвом (страховка таймера)
```

На **Vercel** розклад — у `vercel.json`: один крон `/api/cron?task=all`
раз на добу о 15:05 UTC (на Hobby частіше не можна). Там він не
страховка, а єдиний шлях нагадувань і прострочки; хвилі веде QStash,
крон лише підбирає загублене.

**Не став щохвилини.** Neon на безкоштовному тарифі тарифікує ЧАС РОБОТИ
вичислювача, а не кількість запитів: база засинає в простої й прокидається
на першому ж запиті. Крон раз на хвилину не давав їй заснути ніколи —
місячна квота вигорала приблизно за тиждень навіть при нульовому трафіку.
Це саме та причина, через яку хвилі переїхали в пам'ять процесу.

Той самий принцип діє для будь-якої періодики: перш ніж додавати щось, що
ходить у базу за розкладом, спитай себе, чи не тримає воно її розбудженою
цілодобово.

### 6. AI-агент (чат-помічник), без окремого персонажа

`src/lib/server/zunor/` — логіка агента, що веде діалог з клієнтом
(`agent.ts`), звертається до DeepSeek (`deepseek.ts`), визначає категорію
послуги (`detect-service.ts`, `service-rules.ts`) і будує промпт
(`prompt.ts`). **Окремого персонажа «Zuna» більше немає** — концепт прибрано,
асистент говорить від імені платформи як «Zunor» (третя особа: «Zunor
враховуватиме це…», див. `src/routes/(auth)/dashboard/settings/assistant/`).
Не додавай ім'я «Zuna» і не звертайся від першої особи як окремий персонаж.
У коді згадок не лишилось; натрапиш на них у старих гілках — не перенось.

Тон лишається теплим і людяним (не казенним, «Заявку створено» →
«Готово, я вже шукаю майстра» — цей принцип із `MANIFESTO.md` актуальний),
просто без персоніфікації в конкретного «героя».

**Незавершений діалог живе в localStorage, а не в БД.**
`$lib/zunor/dialog-storage.ts` — ключ на userId, TTL доба, стеля на розмір.
Причина: `/api/zunor/chat` stateless (отримує всю історію в тілі), тож для
переживання F5 сервер не потрібен взагалі, а кожен втрачений хід — це
повторно витрачені гроші на DeepSeek. Писати чернетки розмов у базу не
треба: туди їде лише готова заявка.

Зберігай у стабільних точках (кінець ходу, зміни з фото), **не через
`$effect`** — ефект спрацьовував би на кожному кадрі друкарки. Після
створення заявки клич `clearDialog`.

Правила чату `/dashboard/jobs/new`, на які спирається код:

- **Формат відповіді — один протокол на три файли**: промпт
  (`prompt.ts`) дозволяє `**жирне**`, «— » і «1. », сервер зводить
  `* `/`- ` до «— » (`normalizeListMarkers`), а розбирає все
  `$lib/zunor/message-format.ts`. `MessageBody` лише малює блоки й
  `{@html}` не має. Додаєш елемент формату — міняй усі три місця.
- **Збій і «Стоп» — це `notice`, а не репліка Zunor.** Примітки в
  історію для моделі не потрапляють (`apiHistory`), інакше «Щось пішло не
  так» ставало б словами асистента.
- **«Стоп» мусить зупиняти й гроші.** Клієнт обриває fetch, сервер у
  `cancel()` потоку обриває запит до DeepSeek і НЕ запускає фолбек-хід
  (`api/zunor/chat`). Новий шлях виклику моделі — передавай туди той
  самий `signal`.
- **Хід, обірваний скиданням розмови** (`discardTurn`), нічого не пише:
  ні примітки, ні збереження. Інакше хвіст старої розмови падав би в нову.
- **Обрана послуга «липка»** (`detect-service.ts`): згадка іншої послуги
  у відповіді («вікна теж») — це деталь, а не новий вибір. Перемикає лише
  явна зміна наміру («хоча», «лучше», «замість») або натиснута кнопка з
  назвою послуги. Синоніми — повними формами, не коренем: «звичайн»
  ловив би «звичайно» в будь-якій репліці.
- **Опис заявки (`description`) — повний, для майстра**: звʼязним
  текстом, зазвичай 3–6 речень — що й де, що саме зробити, умови,
  побажання (правило в `prompt.ts` і в схемі інструмента в `agent.ts`,
  міняються разом). Лише факти з розмови: без вигадок, порад, заперечень
  і невідомого; без дати (вона відносна й застаріває), адреси, ціни,
  контактів і фото. Раніше опис мусив оминати все, що є в полях, і
  виходило «Один санвузол. Живе кіт.» — майстрові з цього нічого не
  зрозуміло.
- **Про сервіс агент відповідає лише `SERVICE_FACTS`** (`prompt.ts`):
  як обирають майстра, оплата, комісія, де скасувати заявку. Без цього
  блоку модель дописувала правдоподібне («майстри проходять перевірку»,
  «допоможе підтримка»). Змінився продукт — онови блок, інакше агент
  казатиме клієнтам неправду.
- **Мова розмови — uk / ru / en** (`detectLang`): нічия — українська,
  латиниця — англійська. Кнопки-страховки (`PHOTO_CHIPS`) — мовою
  розмови. Заявка (title/description) — завжди українською: російську
  копію `russianCopy` один раз повертає на переклад, далі приймає.
- **Кнопки на закритих питаннях не залежать лише від моделі.** Рядок
  `>>>` вона губить (дата, кімнати, сторона миття), тож `toMessage` в
  `agent.ts` — один шлях для стріму, синхронного ходу й питання після
  невалідного драфта: кнопки моделі → фото-страховка → `questionChips`
  (`chips.ts`). Кнопок НЕ отримують відкриті й складені питання (два в
  одному, список «— …») — це важливіше за повноту: «Завтра | Четвер» під
  «зранку чи ввечері?» гірше, ніж нічого. Новий закритий крок воронки —
  шаблон у `ASKS` плюс негативний тест на схоже питання. Підписи послуг
  мусить впізнавати `detect-service` (тест у `zunor-chips.test.ts`).
- **Крок 5 у `service-rules.ts` — план повідомлень, а не перелік тем.**
  Перелік тем модель складала в стіну з 4–6 питань або губила головне
  (площу, обсяг сміття). Міняєш план — проганяй сценарії з
  `docs/zunor-test-dialogs.md`: поведінку моделі тести не ловлять.
- Анімація «думає» — `ZunorMarkAnimated animation="thinking"`: кілька
  сценок-маркерів, що грають у випадковому порядку (`shuffle`). JSON не
  правиться руками — його збирає `scripts/animations/zunor-mark-thinking.cjs`
  з контурів `zunor-mark-blink.json`. Кожна сценка мусить починатись і
  закінчуватись нейтральною позою, інакше на стику буде ривок. Монохромна
  через `lottie-mono`: тіло — білий (→ колір тексту), очі — чорний
  (→ колір фону).

Тестові сценарії для ручної перевірки діалогу — `docs/zunor-test-dialogs.md`.
Онови/додай туди сценарій, якщо міняєш логіку `agent.ts` чи `prompt.ts`.

### 6.1. Бейджі й список чатів — з клієнта, не з лоадерів

Лічильники непрочитаних і список чатів **не вантажаться в серверних
`load`**. Вони живуть у сторах (`stores/chat-store.svelte.ts`,
`notifications/store.svelte.ts`), які роблять по одному запиту за сесію
(`/api/chats`, `/api/me/badges`) і далі оновлюються подіями Pusher.

Виняток один: `/dashboard/messages`, де список чатів — зміст сторінки,
тому приходить із SSR (`messages/+layout.server.ts`).

Не повертай `badges`/`chats` з кореневого чи `(auth)`-лейауту: вони
виконуються на КОЖНІЙ навігації, і це були 3-5 запитів до бази за кожен
перехід між сторінками дашборда заради даних, які й так є в браузері.

**Лічильник у бейджі й лічильник на сторінці — одне число, не два.**
Сторінка сповіщень свого `unreadCount` не тримає: вона читає й править
той самий `notifications.unreadCount`, що світиться в панелі та на
мобільній кнопці її відкриття. Доки чисел було два, прочитане на сторінці гасило
лише сторінку, а бейдж у сайдбарі висів далі — їх ніхто не зводив.
З тієї ж причини сторінка не робить власного `channel.bind`: підписка
одна, у сторі, а слухачі чіпляються через `notifications.onNotification()`.
Друга підписка вже колись розійшлась із сервером по імені події
(`'notification'` проти `'notification:new'`) і мовчки не працювала.

**Стор — модульний синглтон, на сервері він спільний для всіх запитів.**
Тому писати в нього дані користувача під час SSR не можна: число одного
відвідувача поїде в HTML наступному. Синхронізація SSR-значення зі
стором іде тільки під `if (browser)`, а розмітка на сервері читає проп
напряму (див. `notification-list.svelte`).

### 6.1.1. Чат (`/dashboard/messages`) — як Telegram

`components/chat/*` — повноцінний месенджер (MANIFESTO, «Чат»): відповіді
з переходом до цитати, реакції, «у мережі», ✓✓, чернетки, галерея фото,
меню правою кнопкою / довгим дотиком, свайп для відповіді. Правила:

- **Шапка чату (співрозмовник, «у мережі», межі прочитаного) — лише
  `loadChatDetails` з `$lib/server/chat-details`**: сторінка чату й
  `GET /api/chats/[id]` (застосунок). Перевірка членства — там же; не
  учасник — null, назовні 404.
- **Повідомлення з бази — лише через `$lib/server/chat-messages`**
  (`MESSAGE_SELECT` + `toChatMessage`): сторінка чату, догрузка й POST.
  Коли кожен шлях мав свою копію select, нове поле дописувалось тричі.
  Там же правило «видалене не віддається»: ні текст, ні вкладення, ні
  реакції, ні текст у цитаті відповіді на нього.
- **Реакції — одна від людини на повідомлення** (`MessageReaction`, PK
  повідомлення + людина), набір закритий (`components/chat/reactions.ts`,
  спільний для браузера й сервера). Сервер ставить рівно те, що прийшло
  (`emoji` чи `null`), а «та сама ще раз — зняти» вирішує браузер
  (`nextReaction`): повтор запиту після обриву не перемикає туди-сюди.
  Подія `message:reaction` несе ПОВНИЙ стан, не різницю.
- **✓✓ — від `lastReadAt` співрозмовника** (`ChatDetails.peerLastReadAt`,
  `ChatPreview.peerLastReadAt`), на кожному своєму повідомленні. Не
  плутати з `myLastReadAt`: з нього межа «Непрочитані повідомлення».
- **«У мережі» — з presence** (`lastSeenMany` + `User.lastSeen`), а подія
  від співрозмовника (пише, друкує, прочитав) одразу робить його «у
  мережі». Окремого опитування сервера немає й не треба.
- **Меню повідомлення одне** — `ContextMenu` з bits-ui (права кнопка й
  довгий дотик). Кнопка-смайлик біля бульбашки не має свого меню, а
  відкриває це ж подією `contextmenu`. Обробники тригера зливаються через
  `mergeProps`: на pointer-подіях bits-ui тримає довгий дотик, і свайп
  без злиття його перетер би.
- **Посилання — `linkify`, не `{@html}`**: лише http(s) і www.
- **Картка посилання живе в самому повідомленні** (`Message.linkPreview`,
  як у Telegram), а не тягнеться при кожному перегляді. Роут пише
  повідомлення з тим, що вже є в кеші, а за невідомою карткою йде ПІСЛЯ
  відповіді (`attachLinkPreview` у `$lib/server/chat-link-preview`) і шле
  `message:preview`. Правка з іншим посиланням картку скидає. Тягне її
  лише `$lib/server/link-preview` — правила SSRF у розділі 2.2. Картинки
  в картці немає навмисно: її вантажив би браузер співрозмовника напряму
  з чужого сервера (піксель-трекер з IP і часом прочитання).
- **Чернетки — localStorage** (`drafts.svelte.ts`, ключ користувач + чат,
  стеля 50), як і незавершений діалог із Zunor. Поле вводу одне на всі
  чати, тож при зміні чату текст береться з чернетки нового.
- **Шпалери — `chat-background.svelte`**, під відкритим чатом і під
  порожнім станом «Оберіть чат». Світла тема — стандартний градієнт
  Telegram (чотири кольори `--mesh-*` у самому компоненті) і SVG-візерунок
  `static/chat-pattern.svg` поверх нього через `soft-light`; темна — лише
  візерунок. Точки кольорів — Telegram-івські, віддзеркалені по вертикалі:
  так розклад збігається з його (звірено рендером зі скриншотом). Плашки
  над шпалерами (дата, «Оберіть чат») — токен `--chat-service`, а не
  біла картка; вхідний пузир — `--bubble-in` (білий на світлій темі).
- **Пошук і фільтр списку чатів — як у Telegram.** Пошук — капсула з
  фоном і рамкою поля (див. 7.1), у фокусі рамка й лупа кольору акценту. «Усі / Непрочитані» —
  `components/segmented-control.svelte`: підкладка на двох пружинах
  (передній край швидкий, задній мʼякий із перельотом), тому вона
  «гумово» розтягується в дорозі. Новий перемикач-пігулку беремо його,
  а не `ui/tabs`.

### 6.2. Що можна взяти без запиту до БД

Перед тим як писати `prisma.*` у `load`, перевір, чи цього немає під рукою:

- **Роль, `onboarded`, `emailVerified`, `banned`** — `locals.account`, його
  вже прочитав `guardHandle` на `/dashboard/**`. Окремий
  `prisma.user.findUnique({ select: { role: true } })` у роуті — це другий
  SELECT за ту саму колонку. Фолбек (`locals.account?.role ?? 'CLIENT'`)
  лишай: поза `/dashboard/**` `account` не заповнюється.
- **Міста й категорії** — `$lib/server/reference.ts` (`getCities`,
  `getCategories`). Кеш у пам'яті процесу з TTL 10 хв, як і решта стану
  (розділ 2.1). Це найстабільніші дані в системі; читати їх із БД у лоадері,
  який спрацьовує на кожен вхід на сторінку, означає будити Neon даремно.
  Той самий кеш обслуговує `/api/cities` і `/api/categories`.

І загальне правило для `load`: запити, які **не залежать один від одного**,
запускай через `Promise.all`. Послідовні `await` — це послідовні round-trip
до бази; на Neon вони помітні. Перевірка доступу від цього не страждає, якщо
результат другого запиту віддається назовні ЛИШЕ після перевірки першого
(так зроблено в `messages/[chatId]/+page.server.ts`).

### 7. Тости — тільки `svelte-hot-french-toast`

Проєкт використовує бібліотеку
[`svelte-hot-french-toast`](https://svelte-hot-french-toast.vercel.app/)
(вже в `package.json`). `<Toaster>` підключений один раз у кореневому
`src/routes/+layout.svelte` з кастомними `toastOptions` (стилі під тему
проєкту, `class: 'app-toast'`) — **не додавай другий `<Toaster>`** в інших
лейаутах чи сторінках.

Виклик з будь-якого клієнтського коду:

```ts
import toast from 'svelte-hot-french-toast'

toast.success('Збережено')
toast.error(j?.message ?? 'Не вдалося зберегти')
toast('Просте повідомлення', { icon: SomeIcon })
```

Правила ті самі, що й для будь-якого клієнтського UI-стану: виклик тільки в
браузерному коді (обробники подій, `onMount`, `$effect`), не в
`load`/actions на сервері. Щоб показати серверну помилку — поверни текст з
ендпоінта і виклич `toast.error(text)` на клієнті (див. приклад у
`src/routes/(auth)/dashboard/settings/assistant/+page.svelte`).

Для нотифікацій із realtime (Pusher) є окрема обгортка
`src/lib/notifications/toast.ts` (`showNotificationToast`) — вона одна
знає мапінг типу нотифікації на вигляд тоста; не дублюй цю логіку в
компонентах, викликай саме її.

Сповіщення показуються не текстовим тостом, а **карткою з дією**
(`notifications/island.svelte`, як сповіщення macOS): плитка-іконка
кольору події, «Нова заявка · щойно», заголовок, подробиці й кнопка дії
(«Переглянути заявку», «Залишити відгук») — до заявки чи замовлення
один дотик. Поверхня — тієї ж теми, що й застосунок, з рамкою й тінню;
картка завжди в правому верхньому куті: на компʼютері виїжджає з-за
правого краю з легкою пружиною й іде туди ж, як у macOS, на телефоні
падає згори, як банер iPhone. Чорний «острів» у стилі Dynamic Island, що був тут раніше,
на світлій сторінці виглядав чужим — назва файлу лишилась від нього.
Це той самий `<Toaster>`: картка йде через
`toast.custom(Island, { props, position })`, таймер, пауза під курсором і
черга — бібліотечні, компонент лише реагує на `toast.visible`. Правила:

- **Новий тип сповіщення — два записи**: слова (ярлик над заголовком,
  напис дії — що станеться, а не «Відкрити») — у `KIND_TEXT`
  (`notifications/kinds.ts`, спільні з Telegram), іконка й тон — у
  `KINDS` (`toast.ts`). Без запису картка загальна, а не зламана. Адреса —
  завжди `linkFor`, та сама, що в стрічці сповіщень і в кнопці Telegram.
  І приклад у `notifications/preview.svelte`.
- **Перевірка вигляду — кнопка «Сповіщення» на `/dashboard`**, лише в
  dev (`notifications/preview.svelte`): кожен тип через справжній
  `showNotificationToast`. Тексти там — копія серверних
  (`server/notifications.ts`), міняються разом.
- **Прочитаним позначає лише перехід** — колбеком зі стора, а не
  імпортом стора в `toast.ts` (вони імпортували б один одного по колу).
  «Пізніше» і хрестик лише закривають.
- **id картки — з id сповіщення**: подія, що прийшла двічі, не дасть
  двох карток.
- **На екрані не більше трьох карток** і не більше, ніж влазить у
  висоту вікна (`makeRoom` у `toast.ts`): зайву, найстарішу, закриваємо.
  Бібліотека складає тости стовпчиком без обмеження, і пачка сповіщень
  їхала за нижній край. Сповіщення не губиться — воно в стрічці.
- **Переозначення стилів обгортки бібліотеки — з вагою більшою за її
  власну** (`.wrapper > .message:has(...)`), а не рівною: при рівній
  перемагає той CSS, що підвантажився пізніше, і в dev це була
  бібліотека — картка ставала посередині, хоча на збірці стояла в куті.
- Обгортка бібліотеки — смуга на всю ширину; картка вимикає їй
  `pointer-events`, інакше вона перехоплювала б кліки по шапці поруч.
- **Класи в `<style>` компонентів не називай іменем утиліти Tailwind**
  (`ring`, `border`, `shadow`, `truncate`…): Tailwind бачить слово в
  розмітці й генерує утиліту, яка ляже поверх твоїх стилів. Кільце часу
  з класом `ring` отримало рамку 1px і малювало квадрат.

**«Скопійовано» — плашка посередині екрана, а не тост у куті**, як у
Telegram: `copyToClipboard(value, 'Текст скопійовано')` з
`$lib/utils/clipboard` (вигляд — `components/copied-toast.svelte`). Це
той самий `<Toaster>`: custom-тост у позиції `bottom-center` — окрема
черга, тож картки сповіщень угорі її не зсувають; у центр вікна обгортку
ставить сам компонент. Повторне копіювання прибирає попередню плашку
(`toast.remove`) і показує нову, з новим id.

**id тоста не перевикористовуй.** `svelte-hot-french-toast` 4.0.0
памʼятає таймер закриття за id і після спрацювання його не забуває: тост,
показаний вдруге з тим самим id, таймера вже не отримує й висить на
екрані назавжди (так залипала плашка «Скопійовано» зі сталим id). Тому:
новий показ — новий id; повтор того самого (сповіщення за id події) —
пропустити, поки старий ще в списку бібліотеки, а не оновлювати. Свого
`navigator.clipboard.writeText` + `toast.success('Скопійовано')` у
компонентах не пишемо: збій буфера там здебільшого ковтався мовчки.

Старого кастомного тостера (`stores/toast-store.svelte.ts`,
`components/toast/*`, `toster.md`) у проєкті вже НЕМАЄ — видалений. Якщо
натрапиш на згадку про нього у старому коді чи коментарях, це слід
прибрати, а не відновлювати.

**Коли тост потрібен, а коли ні.** Тост — не нагорода за кожну дію, а
відповідь на питання «що щойно сталося?». Ставимо його, коли інакше на це
питання відповіді немає:

- сторінка після дії **змінюється на іншу** (скасування заявки, вибір
  майстра) — на новому екрані про подію вже нічого не написано;
- форма після успіху **зникає** (відгук про співпрацю, відгук на заявку) —
  саме так виглядав би і збій, що стер написане;
- дія означає домовленість або коштувала б грошей (старт і завершення
  роботи, вибір майстра);
- дія **не дала видимого результату** — тоді тост із помилкою обов'язковий.
  Мовчазна невдача гірша за будь-яке повідомлення.

Тоста НЕ треба, коли результат видно очима: повідомлення з'явилось у
стрічці чату, фото стало в галерею, бейдж непрочитаних згас, статус на
сторінці змінився поруч із кнопкою. Тост поверх очевидного — шум.

Помилки форм лишаються **під полем**, а не в тості: там на них дивляться,
і вони не зникають за чотири секунди. Тост із помилкою — для дій без
форми (кнопка в списку, дія над рядком).

Оптимістичне оновлення, яке не підтвердив сервер, треба **відкотити**
(див. `notifications/store.svelte.ts`): інтерфейс не має показувати те,
чого на сервері не сталось.

### 7.1. Картки форм — тільки через `$lib/components/settings`

Згруповані картки (налаштування, онбординг, профіль) збираються з чотирьох
компонентів, і власної розмітки картки в сторінках бути не повинно:

| Компонент       | Для чого                                       |
| --------------- | ---------------------------------------------- |
| `SettingsGroup` | Заголовок + картка + виноска під нею           |
| `SettingsField` | Поле форми: підпис ліворуч, контрол праворуч   |
| `SettingsRow`   | Підпис + опис ліворуч, кнопка/статус праворуч  |
| `SettingsBlock` | Блок на всю ширину: textarea, чіпи, вибір теми |

Візуальна мова одна на весь застосунок: `rounded-xl bg-muted/40 py-1` для
картки, `mx-4` + `border-t border-border/60 first:border-t-0` для рядків
(лінія втоплена від країв, як в iOS). Рамки з `divide-y` більше немає —
раніше нею користувались два розділи налаштувань, і вони виглядали як
шматок іншого застосунку.

Роздільник ставить сам рядок через `:first-child` — сторінка не розставляє
модифікатори руками. Ширину колонки з контролом (`sm:w-[56%] sm:max-w-75`)
знає лише `SettingsField`: раніше цей рядок класів був скопійований у
дев'ять місць, і копії вже почали розходитись у записі.

**Поле вводу — один вигляд на весь застосунок:** фон `--field`, рамка
`--input` (у кабінеті — палітра Perplexity: поле біле / #1f2125, рамка —
border-base, 15% / 14% кольору тексту). Їх ставлять
самі `ui/input`, `ui/textarea`, `ui/select`, `ui/input-otp`, і сторінка
фон поля не перебиває: `bg-background` на `Input` давав у темній темі
поля кольору сторінки поруч зі звичайними. У фокусі поле стає кольору
сторінки (`bg-background`) з рамкою акценту — як у GitHub; у світлій
темі обидва білі. Своє поле (капсула пошуку чатів, кнопка-список міста й
району, `FloatingInput`, поля ручної заявки) — на тих самих правилах.

Назва історична — компоненти обслуговують і онбординг теж. Це той самий
екран (`/settings/profile` рендерить форму онбордингу в `mode="edit"`).

**Три подачі, одні компоненти** (`settings/layout.ts`).
`/dashboard/settings/**` — повноцінна сторінка (не модалка) у подачі
GitHub (`setSettingsLayout('stacked')` у лейауті налаштувань): меню
розділів ліворуч (активний — сіра плашка й смужка акценту), праворуч
одна колонка — заголовок розділу з лінією, поля одне під одним, жирний
підпис, поле не ширше 440px, підказка текстом під полем, кнопки форми
під полями ліворуч. Шапки з аватаром над розділами немає навмисно. Кроки
онбордингу — `split` (`onboarding-wizard`), без контексту — картка.
Сторінка розділу про подачу не знає й не повинна; довгий текст
(«Про себе») у stacked — теж `SettingsField`, а не `SettingsBlock`, щоб
мати ту саму ширину.

**Пояснення в налаштуваннях — короткі й лише там, де потрібні.** Одне
речення, без «чому»: «Чіткіший текст і рамки», «Діє лише в цьому
браузері», «Заявки далі обраної відстані не надсилаємо». Пояснення там,
де без нього людина помилиться чи не зрозуміє наслідку: незворотність,
модерація, хто бачить дані, де діє налаштування, що зміниться. Там, де
контрол показує себе сам (зразки акценту, мініатюри теми), — без
пояснень.

**Акцентний колір і контраст** — `$lib/stores/appearance.svelte.ts`,
localStorage + атрибут на `<html>` (`data-accent`, `data-contrast`). Самі
кольори — ТІЛЬКИ в `layout.css` (`[data-accent='…']`): зразок у палітрі
несе свій `data-accent` і малює себе через `bg-primary`, тож копії hex-ів
у TS немає. До першого кадру атрибути ставить скрипт в `app.html` — ключі
сховища міняти лише разом із ним. Тому ж `--ring` і `--primary-hover`
виведені з `--primary`, а не записані кольором: інакше фокус і ховер
лишались би синіми при будь-якому акценті.

**Темна тема — лише в кабінеті (`/dashboard/**`).** Лендинг, вхід і
реєстрація, профілі майстрів, «Про нас» — завжди світлі, хоч би що
людина обрала в налаштуваннях. Тому клас `dark` на `<html>` ставить не
mode-watcher (у нього порожній `darkClassNames`, він лише памʼятає
вибір), а скрипт в `app.html` до першого кадру і ефект у кореневому
`+layout.svelte` — обидва за правилом `isThemedPath` із
`$lib/theme-scope`. Міняєш правило — міняй обидва місця.
`color-scheme` теж іде за класом (`layout.css`), а не за inline-стилем
mode-watcher. Перемикача теми поза кабінетом бути не повинно.

**Палітра кабінету — токени Perplexity**, зняті з їхнього CSS
(perplexity.ai) і звірені піпеткою зі скриншотами в `docs/`. Світла —
блок `.in-app` у `layout.css` (клас на `<html>` ставить те саме правило
`isThemedPath`, що й `dark`, тож лендинг лишається на своїй палітрі):
сторінка #fbfbfb, картки й меню білі, текст #0b2833, другорядний
#475d65. Темна — `.dark`: #15171b / #1b1d21 / #212327, текст #dbdee3.
Лінії, рамки й ховери — напівпрозорі, як в оригіналі (border-soft 7%,
border-base 14–15%, bg-soft 6–7%): на панелі, картці й сторінці вони
дають ті самі кольори, що в Perplexity. Тому в непрозорий колір їх не
«запікай» — на іншому тлі він розійдеться з оригіналом.

**Кнопки й меню — пласкі, у стилі Perplexity.** `ui/button`:
заокруглення 8px, суцільна заливка без градієнта й тіні; акцентна
(default = primary), сіра secondary без рамки, outline — тонка рамка на
прозорому. `ui/dropdown-menu`: скруглення 12px, мʼяка тінь, рамка
border-base, пункти 36px / 8px / 15px, роздільник із відступами.
Фільтри «Показати: …» свого вигляду меню не задають — лише ширину; пункт
«усі» відділений роздільником.

**Іконки — один набір, стиль Hugeicons Stroke Rounded** (MIT): лінія 1.5
на сітці 24, мʼякі кути, без анімацій. Lucide в проєкті більше немає.
Загальні іконки — `$lib/components/icons/set/<імʼя>.svelte` (імена як у
lucide: `check`, `chevron-down`, `trash-2`), імпорт поштучно; продуктові
імена (`JobsIcon`, `OrdersIcon`…) — з `$lib/components/icons`. Файли в
`set/` генерує `scripts/icons/build-icons.mjs` з контурів пакета
`@hugeicons/core-free-icons` (сам пакет у залежностях не тримаємо — як
запустити, написано в шапці скрипта); руками їх не правимо. Нова
іконка — рядок у його таблиці й перезапуск. Пропи ті самі, що в lucide
(`size`, `strokeWidth`, `class`, атрибути svg), за замовчуванням 24px.
`shadcn-svelte add` приносить імпорти lucide (`components.json` досі
каже `iconLibrary: lucide`) — після нього заміни їх на `set/`.
Виняток — іконки послуг (`service-icon.svelte`, контент категорії) і
рядкові svg переглядача фото (`photo-lightbox.ts`, ті самі контури).

**Стартовий екран заявки (`jobs/new`)** — кольори поля вводу Perplexity
(зняті піпеткою зі скриншота): поле сіре (світла тема #f0f0f0, темна
`--field` #1f2125, рамка `--input`, у темній ще мʼяка тінь назовні), а не
біле, як звичайні поля форм; іконки в спокої — 65% тексту поверх поля
(`--composer-icon`, у темній рівно #999ca1), підказка — 50%, кнопка
«Надіслати» — колір тексту з іконкою кольору сторінки, як «Стоп». Під
полем дві картки-способи кольорами карток Perplexity: розмова — бірюза
#016a71 зі світлою плямою #37949a у правому верхньому куті, форма без
чату — майже чорна бірюза #081f22 з плямою #0f454b (градієнти звірені
рендером зі скриншотом). Колір сталий, не від акценту, однаковий в обох
темах.

**Тема перемикається лише через `switchTheme(next, кнопка)`**
(`$lib/theme-transition`), а не `setMode` напряму: так темна тема
розходиться колом від кнопки, а світла стягує її назад, як у Telegram
(View Transitions — браузер анімує маску над двома знятими кадрами, кола —
у `layout.css`). Без підтримки API чи зі «зменшити рух» — миттєво. Клас
`dark` модуль ставить сам, синхронно: `mode-watcher` робить це лише в
наступному кадрі, і кадр «після» знявся б ще в старій темі.

### 8. Svelte 5 runes

`runes: true` примусово ввімкнено для всього коду проєкту (крім
`node_modules`) у `svelte.config.js`. Пиши стори через `$state`/`$derived`
(файли `*.svelte.ts`), не через застарілі `writable`/`derived` зі
`svelte/store`, якщо для цього немає явної причини сумісності.

Конкретні правила, за якими вирівняний код:

- **`page` беремо з `$app/state`**, не з `$app/stores`. Тобто
  `page.url.pathname`, без `$`-префікса. `$app/stores` у SvelteKit 2
  лишили тільки для сумісності.
- **Похідне значення — `$derived`, а не `$state` + ручний перерахунок.**
  Якщо число можна вивести зі списку (`totalUnread` з `chats`), виводь:
  синхронізоване вручну поле рано чи пізно розійдеться з джерелом, бо
  хтось додасть гілку й забуде викликати перерахунок.
- **Масив/об'єкт, що читає реактивні значення, теж має бути `$derived`.**
  Звичайний `const items = [...]` у рунному компоненті обчислюється один
  раз при монтуванні — бейджі й підписи в ньому застигнуть назавжди.
- **`$effect` — лише для побічних ефектів** (DOM, підписки, таймери,
  імперативні API). Синхронізацію значення зі значенням роби через
  `$derived`; для анімованих величин є `Tween.of(() => ...)`, який сам
  стежить за джерелом і не потребує ефекту.
- **`$state(prop)` — завжди через `untrack`.** Локальна копія пропа
  (`$state(untrack(() => initialJobs))`) — легітимний патерн, але компілятор
  інакше видає `state_referenced_locally`, і з коду не видно, це рішення чи
  недогляд. `untrack` каже прямо: беремо ПОЧАТКОВИЙ знімок, далі стан живе
  сам. Якщо ж значення має стежити за пропом — це не `$state`, а `$derived`.

Перевірка: `npm run check` не повинен додавати попереджень із посиланнями на
`svelte.dev/e/state_referenced_locally` — усі такі місця вже або `untrack`,
або `$derived`.

### 7.2. Панель дашборда — компоненти shadcn, логіка наша

`/dashboard/**` користується `$lib/components/ui/sidebar` (блок
`sidebar-07` із shadcn-svelte). Своєї розмітки панелі в проєкті немає:

| Файл                              | Що в ньому                                       |
| --------------------------------- | ------------------------------------------------ |
| `dashboard/app-sidebar.svelte`    | склад пунктів, роль, бейджі, активний рядок      |
| `dashboard/nav-user.svelte`       | рядок користувача в підвалі (посилання, не меню) |
| `dashboard/mobile-trigger.svelte` | кнопка відкриття на телефоні + лічильник         |

Наслідки, на які спирається код:

- **Окремого мобільного меню немає.** На вузькому екрані `Sidebar` сам
  показує себе шторкою. Колишній `bottom-nav` видалено: два меню з тими
  самими пунктами рано чи пізно розходяться складом.
- **Стан «згорнуто» веде `Sidebar.Provider`** і сам пише cookie
  `sidebar_state`. Лейаут читає її до рендеру (`+layout.server.ts`), щоб
  панель не мигала. Ім'я cookie беремо з `ui/sidebar/constants.js`, а не
  рядком — інакше вони розійдуться при наступному оновленні блока.
- **Ховер на логотипі ловимо через `mouseover`, а не `mouseenter`.**
  Після згортання кнопкою курсор лишається ВСЕРЕДИНІ панелі, нового
  `mouseenter` не буде — і кнопка розгортання не з'явиться, доки не
  відвести мишу й повернути. `mouseover` спливає з дітей і приходить на
  кожен рух.
- **Тултипи пунктів вимагають `Tooltip.Provider`**, який дає той самий
  `Sidebar.Provider`. Тому в тестах панель рендериться через
  `fixtures/sidebar-host.svelte`, а не напряму.
- **Вигляд панелі — за референсом у `docs/`** (скриншоти, обидві теми).
  `variant="sidebar"`, не inset: контент стоїть упритул до панелі без
  вікна й відступів, межу тримає лінія `--sidebar-border`. Панель —
  свого тону `--sidebar-raised` (світла #f3f3f3 на #fbfbfb, темна
  #1b1d21 на #15171b), активний пункт — `--sidebar-active`, ховер —
  `--sidebar-accent`. Активний пункт ловимо за НАЯВНІСТЮ `data-active`
  (MenuButton ставить порожній рядок), а не `='true'`. Пункти 40px, скруглення 8px, підпис
  15px, іконка 20px кольору тексту. Розгорнута — 15rem, угорі знак і
  назва Zunor та кнопка згортання; унизу налаштування, лінія на всю
  ширину й рядок користувача (аватар, імʼя, стрілка → профіль). Рейка —
  57px (8 + квадрат 40 + 8 + 1px лінії). Прокручується документ,
  виняток — чати (`isChat`): там контент рівно на екран. Розгортає
  кнопка на місці знака в рейці (наведення міняє знак на іконку панелі;
  вона ж клавіатурний шлях) і клік по порожньому місцю рейки
  (`expandFromRail`: клік по пункту чи кнопці панель не чіпає).
- **У повідомленнях панелі немає.** `/dashboard/messages/**` — окремий
  екран зі своїм меню ліворуч (список чатів): лейаут дашборда передає
  `AppSidebar away`, і панель відʼїжджає за лівий край (стан «розгорнуто»
  й cookie не чіпаються), а мобільну кнопку меню заміняє «Назад» ліворуч
  від пошуку в списку чатів. **Налаштування — з панеллю**: меню розділів
  стоїть поруч із нею, «Назад» там немає, а на телефоні смуга розділів
  лишає ліворуч місце під кнопку панелі. «Назад» веде на
  сторінку, з якої зайшли в розділ, а не на попередній розділ чи чат:
  адресу памʼятає `$lib/utils/entry-point.svelte` (`entryPoint` у
  лейауті розділу; для вкладених компонентів — `provideEntryPoint` /
  `useEntryPoint`). Відкрили напряму — на `/dashboard`. Новий
  повноекранний розділ — той самий помічник, а не ще одна копія
  `afterNavigate`.
- **`Sidebar.Rail` не використовуємо.** Блок sidebar-07 малює нею
  невидиму смугу 16px ПОВЕРХ контенту праворуч від панелі (`-right-4`,
  `z-20`), яка перемикає панель по кліку. З нашим перемикачем на
  логотипі вона зайва, а шкодить помітно: перехоплює кліки по лівому
  краю сторінки, підміняє курсор на `resize` там, де нічого не
  тягнеться, і дає «панель сама згорнулась». На це є тест — рейки в
  розмітці бути не повинно.

### 7.3. Списки заявок (`/dashboard/jobs`)

«Мої заявки» клієнта й стрічка майстра малюються однією карткою —
`components/jobs/job-card.svelte`. Правила, на які вона спирається:

- **Картка як вакансія на work.ua**: велика назва, під нею факти
  рядками з сірими іконками — бюджет жирним, послуга · день, замовник із
  рейтингом і район · відстань (майстрові; картка отримує їх даними —
  пропи `client` і `place`, а не розміткою), характеристики через « · »
  (`jobTags` з `describeJob`, без послуги й дня); опис сірим на два
  рядки (повністю — на сторінці заявки); унизу «25 хв тому» ліворуч і
  стан праворуч (клієнтові, снипет `aside`). Лайків, «не цікаво» й
  лічильника пропозицій майстрові немає. Заглушка догрузки
  (`job-card-skeleton`) повторює ту саму форму.
- **Фільтр — компактне меню з іконками послуг** (ті самі
  `service-icon`, що й у картках), а не смуга пілюль.
- **«Топ для тебе»** — проп `match` картки (причини з `bestMatches`),
  як брендована вакансія на work.ua: картка лишається білою, але лежить
  на бірюзовій підкладці Perplexity з градієнтом (#016a71 і світла
  пляма #339196 праворуч унизу, білий текст; стала, не від акценту,
  однакова в обох темах), і з-під неї видно смугу «✦ Топ для тебе
  · Поруч з тобою · …» (`fitReasonLabels` у `jobs/display.ts`). Плашки в
  куті й причин під назвою більше немає. Посилання — уся обгортка разом
  зі смугою. Картка сама нічого не рахує.
- **Замовлення (`/dashboard/orders`) — та сама мова**: колонка
  `max-w-3xl`, `PageHead`, картки одна під одною
  (`orders/order-card.svelte`): «Оновлено …» і стан угорі, рядок фактів із
  ціною, теги (`jobTags` — спільні з карткою заявки), друга сторона внизу.
  Опису немає — замовлення людина вже знає. День — від `createdAt`
  заявки (`fromJob`), не замовлення.
- **Шапка списку (`PageHead`) не липне** — прокручується разом зі
  сторінкою: прилипла забирала на телефоні чверть екрана з-під карток.
- **Стан для клієнта — його словами** (`jobState` у `jobs/display.ts`,
  плашка — `jobs/job-state.svelte`, одна на список і сторінку заявки):
  «Шукаємо майстра», «N пропозицій», «Майстра обрано». Кольором залитий лише стан
  «є пропозиції» — це місце, де клієнт має щось зробити. Майстрові
  кількість чужих пропозицій НЕ показуємо: «вже 5» відлякувало б новачків
  (MANIFESTO, «Справедливий маркетплейс»).
- **День прибирання — через `resolveWhen` + `formatDay`.** `today`/
  `tomorrow` у metadata відносні до дня СТВОРЕННЯ заявки; показані як є,
  вони тиждень брехали «Завтра». Те саме для `describeJob(meta, createdAt)`.
- **Іконки послуг — власний набір** `categories/cleaning/service-icon.svelte`
  (контент категорії, не загальний набір іконок): контур 1.6, тіло ледь залите, рівно
  одна деталь кольором `--primary`. Нова послуга — нова гілка там же,
  в тій самій мові.
- **`PageHead` без градієнта під собою.** Градієнт лягав на перший рядок
  навіть у спокої й «розмивав» його; межа — волосина, що зʼявляється,
  лише коли під шапкою вже є контент.
- **Сторінка заявки (`jobs/[id]`) — за зразком вакансії work.ua**, у
  тій самій колонці, що й список (`max-w-3xl`). Заявка лежить на одній
  картці (`bg-card`, рамка, скруглення 16px), і все головне видно до
  першої прокрутки: угорі смуга дій — головна кнопка («Подати
  пропозицію» майстрові) і меню ⋮ праворуч (клієнтові — «Скасувати
  заявку», майстрові — профіль замовника й посилання; без головної
  кнопки меню стоїть у рядку «Опубліковано»); далі «Опубліковано ·
  перегляди», плашки
  (стан і «Терміново», коли прибирати сьогодні чи завтра), велика назва
  з іконкою послуги праворуч і факти з сірими іконками (замовник, де,
  коли, що, обсяг, бюджет, телефон «після угоди») — головне рядком,
  пояснення дрібним під ним. Нижче «Про заявку» (опис і фото — що саме
  зробити, клієнт пише там) і «Деталі» — решта характеристик сіткою
  плиток (іконка з `detail-icons.ts`, підпис, значення), предмети
  хімчистки — чипами. Галочок там немає: «2 вікна» чи «5-й поверх» —
  обставини, а не пункти до виконання. Усе це — `jobs/job-summary.svelte`,
  спільний для обох; головну дію він отримує снипетом `actions` (лише
  коли вона є), меню — `menu`. Майстрові внизу картки — заклик
  на візерунку чату (як «Задайте питання» у work.ua): замовник і та сама
  кнопка, щоб не гортати назад; форма пропозиції — картка
  `$lib/components/settings`. Клієнтові пропозиції — ПЕРШИМИ, окремою
  карткою над заявкою: він приходить по сповіщенню «нова пропозиція», і
  його дія — обрати майстра, а заявку він знає. Рядки з волосиною;
  рекомендовану видно з плашки біля імені, а не з кольорової обводки.

- **Редагування заявки** — `/dashboard/jobs/[id]/edit`, пункт «Редагувати
  заявку» в меню ⋮ клієнта; лише власник і лише OPEN. Форма — той самий
  майстер, що й заявка без чату (`components/jobs/job-wizard.svelte`, проп
  `edit`): відкривається на зведенні, кожен пункт веде на свій крок і
  назад. Запис — `PATCH /api/jobs/[id]` → `$lib/server/job-edit`:
  - той самий `validateCleaningMetadata`; площа й поправка асистента, яких
    форма не показує, зберігаються зі старої заявки;
  - «сьогодні/завтра» пишуться ДАТОЮ (у заявці вони рахуються від дня
    створення); стара відносна дата при порівнянні теж переводиться — інакше
    «Зберегти» без правок вважалось би зміною;
  - назва перегенеровується, лише коли змінилось те, з чого вона
    складається (дата й опис назву від асистента не чіпають);
  - статус перевіряється в самому `updateMany` (майстра могли обрати в
    іншій вкладці) — тоді 409;
  - фото — `$lib/server/job-attachments`: нові лише з нашої хмари й теки
    `zunor/users/<id>/jobs/`; прибрані стираються з хмари ПІСЛЯ запису, а
    в формі видалення відкладене (`deferRemove` у `portfolio-uploader`) —
    «Скасувати» не лишає заявку з битим фото;
  - майстрам із пропозицією `SENT` — `JOB_UPDATED` («Клієнт змінив
    заявку»), поки попереднє не прочитане — нового немає;
  - `Job.editedAt` — «змінено …» у рядку «Опубліковано» (не `updatedAt`:
    той рухають перегляди);
  - розсилка НЕ перезапускається: покликані лишаються, нові умови
    стрічка майстрів застосовує сама.

- **Дубль заявки — попередження, а не заборона**
  (`$lib/server/job-duplicates`). Друга заявка на те саме — здебільшого
  випадковість (повтор після збою мережі, форма після чату, нова заявка
  замість правки дати), а майстрам це дві однакові картки й пропозиції в
  порожнечу. Правила:
  - `POST /api/jobs` шукає серед ЖИВИХ заявок клієнта: OPEN, не
    прострочені, день роботи не минув. «Те саме» вирішує категорія —
    `matchingFor(category).duplicateKey` (у прибиранні — послуга; день і
    приміщення не важать);
  - знайшов — 409 `{ message, duplicate }`, заявки й розсилки немає. Форма
    й картка драфту в чаті показують `jobs/duplicate-notice.svelte` над
    кнопкою (картка веде до тієї заявки), а кнопка стає «Все одно
    створити» й шле `allowDuplicate: true` — лише буквальне `true`;
  - попередження привʼязане до того, на що його знайшли: у формі — до
    послуги, у чаті — до конкретного драфту. Інакше «Все одно створити»
    пропустило б перевірку для вже іншої заявки;
  - 409 про дубль — лише ПІСЛЯ решти перевірок (місто, категорія): друга
    спроба не має впертись у помилку, яку можна було показати одразу.

### 7.4. Фото профілю (`avatar-uploader.svelte`)

- **Зміна й видалення — одразу, не з кнопкою «Зберегти» форми.** Файл у
  Cloudinary має фіксований publicId (`zunor/users/<id>/avatar/profile`,
  `upload/signature`) і перезаписується вже при завантаженні, тож
  «відкласти до збереження» не виходило: хмара мала нове фото, база —
  старе посилання. Запис — `api/user/media` (`avatar`), видалення —
  `avatar-remove`; форма лише отримує нові значення через bind.
- **`avatar-remove` стирає за userId із сесії**, publicId у тілі не
  приймає: фіксований id (файл міг потрапити в хмару без запису в базу) і
  старий id із бази, лише якщо він у просторі цього користувача.
- **Обрізання — у браузері** (`avatar-cropper.svelte`): на сервер іде
  квадрат до 1024px у JPEG, не оригінал. Поворот, нахил і дзеркало
  рахуються в одній моделі (зсув у власних осях фото), і експорт малює
  тим самим перетвором, що й сцена, — інакше аватар розійшовся б із тим,
  що людина бачила в колі.
- **Після зміни оновлюй кеш сесії** (`get-session?disableCookieCache=true`,
  потім `invalidateAll`): сесія лежить у cookie 5 хв, і меню показувало б
  старе фото.
- Порожній аватар — градієнт з `--primary` і `CameraAddIcon`; на фото —
  та сама іконка поверх легкого затемнення. Пружинить лише іконка, коло
  стоїть.
- **Повноекранний перегляд фото — лише `$lib/utils/photo-lightbox`**
  (PhotoSwipe): чат, портфоліо в налаштуваннях, `photo-gallery`.
  Мініатюра — `a[data-pswp]` із href на повне фото (`data-cropped`, якщо
  вона обрізана object-cover). Розміри знімка помічник бере з
  мініатюри: із вигаданими 1600×1600 PhotoSwipe розтягував кожне фото в
  квадрат. Вигляд — як у Telegram (`photo-lightbox.css`): іконки
  «видалити / завантажити / наблизити / закрити» вгорі праворуч.
  Кошик — лише з `onDelete` (свої фото). Перегляд має z-index 45, нижче
  діалогів: підтвердження відкривається ПОВЕРХ нього, а `viewer.hold(true)`
  глушить його клавіші, поки питання відкрите.
- **Приклади робіт, на відміну від аватара, зберігаються формою**
  («Зберегти» → `saveMasterProfile` → повторна перевірка). Нове фото
  вже в хмарі й видно в сітці, тож виглядає збереженим — і його
  втрачали, виходячи зі сторінки. Тому в редагуванні: `savedIds` у
  `portfolio-uploader` позначає нові («Нове» + підказка під сіткою), а
  `beforeNavigate` у `master-onboarding` питає «Зберегти нові фото?».
  «Не зберігати» прибирає ці файли з хмари (`portfolio-remove` видаляє
  файл і тоді, коли в базі його немає).

### 7.5. Допомога і скарги

- **«Допомога» — `/dashboard/help`**, пункт у підвалі панелі над
  «Налаштування». Часті питання акордеоном (своєї ролі — першими, роль із
  `data.role` лейаута) і контакти підтримки (`COMPANY.supportEmail`,
  `COMPANY.telegram` з `$lib/legal/company-info`). Факти про сервіс там ті
  самі, що в `SERVICE_FACTS` (`prompt.ts`): **міняються разом**, інакше
  асистент і сторінка казатимуть різне. Чого в продукті немає (страховки,
  гарантії), сторінка так і каже — не обіцяй того, чого немає в коді.
- **Скарга — модель `Report`** (міграція `20261108120000_reports`),
  `POST /api/reports`, діалог `components/reports/report-dialog.svelte`
  (і тиха кнопка з ним — `report-button.svelte`). Де вона є: сторінка
  замовлення (під «Перейти в чат»), меню ⋮ чату, меню ⋮ заявки майстра,
  профіль майстра `/@handle` (лише з акаунтом) і профіль клієнта.
- **Причини — закритий набір** `$lib/reports/reasons.ts`, спільний для
  браузера й сервера, як реакції чату. Ключі читає CRM: додавати можна,
  перейменовувати — ні. «Інше» — лише з поясненням.
- **Контекст скарги перевіряється**: у названому замовленні, чаті чи
  заявці мусять бути обидва — і скаржник, і той, на кого скарга. Інакше
  відповідь «ок / 404» розповідала б, хто з ким працює.
- **Розглядає CRM.** Нова скарга — подія `report:new` на службовому каналі
  (`channels.admin`) з id і причиною, ПІСЛЯ запису; рішення (`status`,
  `resolvedAt`, `resolution`) пише CRM. Повтор тієї самої скарги за добу
  нового запису не створює, а відповідає так само. Людина, на яку
  скаржаться, сповіщення не отримує.

### 7.6. Telegram-бот (сповіщення поза сайтом)

`$lib/server/telegram` на **grammY**. Без `TELEGRAM_BOT_TOKEN` усе
вимкнене: блоку в налаштуваннях немає, сповіщення лише на сайті.

- **Кожне сповіщення дублюється в Telegram через `pushNotification`**
  (`server/notifications.ts`) — це єдина воронка і для `notify()`, і для
  хвиль розсилки. Новий шлях створення сповіщення мусить іти через неї,
  інакше Telegram його не побачить. Модуль бота підвантажується там
  ліниво: grammY не потрібен тестам роутів і диспетчера.
- **Привʼязка — через бота, без таблиці**: лоадер налаштувань сповіщень
  дає посилання `t.me/<бот>?start=<токен>`, бот на `/start` перевіряє
  підписаний токен (`link-token.ts`, HMAC, 15 хв, ≤ 64 символів) і пише
  `User.telegramChatId` (унікальний: один Telegram — один акаунт).
  `/stop` у боті й «Відключити» на сайті відвʼязують. 403 від Telegram
  (бота заблокували) теж відвʼязує — щоб не стукати марно.
- **Прод — вебхук, dev — polling.** На старті процесу (`init` у
  `hooks.server.ts`) бот сам ставить вебхук на
  `BETTER_AUTH_URL/api/telegram/webhook` із секретним заголовком
  (секрети похідні від токена — окремих змінних немає). У dev polling
  запускається, лише якщо вебхука немає: polling знімає вебхук, тож dev із
  продовим токеном вимкнув би бота на проді. **Для розробки — окремий
  бот.** Кнопок із localhost Telegram не приймає — у dev повідомлення без
  кнопки.
- **Чат людини — через кеш** `telegram/chat-cache.ts` (TTL, стеля):
  хвиля — це десятки сповіщень одночасно. Кожна зміна привʼязки кличе
  `forgetChatId`; забанений і видалений у Telegram нічого не отримують.
- Видалення акаунта стирає `telegramChatId` (account-deletion).

### 7.7. Адмінка `/admin`

Замінила окрему CRM (`../crm/` у робочій теці — окремий репозиторій на тій самій базі).
CRM писала в базу напряму й тому обходила правила застосунку: бан діяв із
запізненням (сесії в Redis і кеш стану їй недоступні), майстер не
дізнавався про рішення модерації, «приховане» замовлення лишалось на
сайті, а її застаріла схема з власними міграціями загрожувала скиданням
бази. **Міграції CRM не запускати ніколи.**

- **Два замки, обидва обовʼязкові.** №1 — `adminGate` у
  `hooks.server.ts` (перед `guardHandle`) на все під `/admin` і
  `/api/admin`; №2 — `requireStaff(locals, minRole)` з
  `$lib/server/admin/guard` у КОЖНОМУ load, дії й ендпоінті. Роль — із
  бази (account-cache), не з сесії. Не співробітник, гість, забанений —
  **404**, не 403. Тест `admin-routes.test.ts` сам знаходить усі
  маршрути адмінки й перевіряє це; нова сторінка без гарда впаде там.
- **Другий фактор — свій TOTP** (`admin/totp.ts`, `otpauth`), а не
  плагін better-auth: той оминався б входом через Google. Код питає сама
  адмінка на кожну сесію (`/admin/2fa`, діє 12 год — `step-up.ts`, у
  памʼяті, ключ — id сесії). Секрет у `StaffTwoFactor` зашифрований
  AES-256-GCM ключем із `BETTER_AUTH_SECRET`; той самий код двічі не
  проходить (`lastStep`); 5 спроб за 5 хв. Вхід шле попередження в
  Telegram співробітника. Екран коду — на тій самій рамці, що вхід і
  відновлення пароля (`AuthShell`: відсвіт угорі, знак, колонка 400px;
  клітинки коду — як на підтвердженні пошти), без шапки й підвалу
  сайту (`/admin` у `hiddenLayoutRoutes` кореневого лейауту). QR малює
  `components/admin/qr-code.svelte` з матриці (сервер віддає `0/1`,
  корекція Q): плашка біла в обох темах, тиха зона ≥ 4 модулі,
  виріз під знак ~4% — міняєш вигляд, перевір декодером. Дії сторінки
  іменовані (`?/verify`, `?/lock`): `default` поруч з іменованими
  SvelteKit не пускає (500). Загубив телефон — ADMIN скидає йому 2FA у
  «Співробітники»; єдиний ADMIN — видалити його рядок `StaffTwoFactor` у базі.
- **Ролі** — `$lib/admin/roles.ts`: MODERATOR (анкети, скарги, перегляд
  людини), MANAGER (+ бан, метрики, пошук людей), ADMIN (+ співробітники,
  журнал). Роль видається існуючому акаунту за поштою, не створюється з
  паролем; майстер співробітником бути не може; свою роль і останнього
  ADMIN змінити не можна. Співробітника без анкети `/dashboard` веде в
  `/admin`, а не в онбординг; з анкетою — пункт «Адмінка» в панелі
  кабінету (лише співробітникам). Тому «На сайт» в адмінці й на екрані
  коду — лише з анкетою (`staff.onSite`), інакше це петля назад на
  `/admin/2fa`; вихід звідти — «Вийти з акаунта» (`signOutAndGo` з
  `$lib/utils/sign-out` — один шлях виходу для всіх кнопок «Вийти»).
  Після `signOut` — одразу `goto(to, { invalidateAll: true })`, а не
  `invalidateAll()` поточної сторінки: адмінка без сесії відповідає 404,
  і людина лишалась на сторінці помилки замість головної. Першого ADMIN створює
  `npx tsx prisma/create-admin.ts [пошта]` — акаунт із поштою й
  згенерованим паролем (друкується один раз, у базі хеш better-auth);
  повторний запуск міняє пароль і закриває сесії. Запускає людина сама:
  пароль не має проходити через чат з агентом. Роль руками в Prisma
  Studio не міняй — гард читає її з кешу стану (Redis до 30 хв).
- **Дії — лише через `$lib/server/admin/actions.ts`**, і вони йдуть
  правилами застосунку: бан закриває відкриту роботу (`closeOpenWork` зі
  спільного з видаленням акаунта коду, `cancelWaves`), відкликає сесії
  (`revokeSessions` — і Redis, і база), скидає кеш стану й Telegram;
  рішення модерації й розглянута скарга — сповіщення (`Notify.*`, отже й
  Telegram). Нова дія — тут же, з `logAdmin`.
- **Журнал (`AdminAction`) лише дописується.** Кожна зміна, вхід в
  адмінку й перегляд чату зі скарги (`report.view_chat`) — запис з IP.
  Чат модератор бачить лише в межах скарги на чат і лише останні 30
  повідомлень.
- **Метрики** — `admin/metrics.ts`: медіана часу до першої пропозиції,
  частка з відгуком за 10 хв, без відгуку (серед заявок старших за добу),
  обсяги. Рахуються в памʼяті, стеля 5000 заявок на період.
- **Розсилка не кличе забанених** (`banned: false` у `loadCandidates`).
- Тема — як у кабінеті (`isThemedPath` включає `/admin`, і `app.html`).

### 7.8. Нагадування за день до прибирання

`$lib/server/reminders.ts`: щодня о 18:00 за Києвом обидві сторони
замовлення отримують сповіщення `ORDER_REMINDER` («Нагадуємо: завтра
прибирання», веде на замовлення; через `notify` — отже й у Telegram).

- **Таймер у памʼяті процесу** (`startReminders` з `init` у
  `hooks.server.ts`), крон `reminders` — страховка. Процес піднявся після
  18:00 — прогін одразу. Один запит до бази на добу, не частіше (5.1).
- **Кому**: лише `CREATED` (домовились, не почали), не прибрані, обидві
  сторони не заблоковані, створені не пізніше ніж за 3 год до прогону
  (щойно домовились — нагадування зайве).
- **День роботи дає категорія** — `matchingFor(category).serviceDay`
  (`$lib/categories/matching`), движок про `when` прибирання не знає.
  Відносне «завтра» рахується від дня створення ЗАЯВКИ (`resolveWhen`).
  Категорія без дня — без нагадувань.
- **Двічі не шлемо**: відмітка — `OrderEvent` типу `REMINDER_SENT`
  (міграції не треба), пишеться ДО сповіщень; одночасні таймер і крон
  розводить прапорець `running`. «Історія подій» на сторінці замовлення
  показує `OrderEvent` людям, тож службові типи звідти відфільтровані —
  список `SERVICE_EVENTS` у `$lib/server/order-events.ts`. Нова службова
  відмітка — туди ж.

### 7.9. Мобільний застосунок (`../mobile`) — клієнт цього API

Застосунок на Expo — окремий репозиторій, але бекенд у нього цей:
`/api/*` і вхід `/api/auth/*`. Своєї бізнес-логіки він не має.

- **Вхід — плагін `expo()`** (`@better-auth/expo`) у `auth.ts`, перед
  `sveltekitCookies`. У нативного запиту немає Origin — плагін бере його з
  заголовка `expo-origin`, а той має бути в `trustedOrigins`: `zunor://`
  завжди, `exp://…` (Expo Go) — лише в dev. У проді `exp://` пустив би
  будь-який проєкт з Expo Go.
- **better-auth зафіксований на `~1.6.34`** — тут і в застосунку, версії
  однакові. 1.6.34 закриває вразливості 1.6.5, що стосуються нашого входу
  (захоплення акаунта через Google і через код на пошту); решта відкритих у
  1.6.x — у плагінах, яких у нас немає (magic link, OAuth proxy, вхід із
  пристрою). Перехід на 1.7 — окрема задача: обовʼязкова колонка
  `Account.issuer` з дозаповненням, тож міграція. Оновлювати разом.
- **Відкликати всі сесії людини — `deleteUserSessions(userId)`**
  (`$lib/server/sessions`). `deleteSessions` з 1.6.x приймає лише масив
  токенів: userId туди падав би на `.map`, і бан мовчки лишав би сесії.
- **Контракт API**: застосунок старих версій живе місяцями. Поля
  відповіді не видаляємо й не перейменовуємо, лише додаємо; несумісне —
  новий шлях.
- **Живий канал застосунку — той самий Pusher.** Ключ він бере з
  `GET /api/pusher/config` (публічні `PUBLIC_PUSHER_*`), канали
  підписує `/api/pusher/auth` — тому міняти імена каналів і подій
  (`$lib/server/pusher`) можна лише разом із застосунком (`lib/realtime.ts`
  там), інакше він мовчки перестане отримувати нове.
- **Події однієї дії — одночасно** (`Promise.all`), а не `await` по
  черзі: у надсиланні повідомлення `chat:update` (число на вкладці
  «Чати») чекав відповіді Pusher на `message:new` і приходив на ~200 мс
  пізніше за саме повідомлення, а відповідь відправникові — ще пізніше.
- **Розробка**: сайт — `npm run dev -- --host`, щоб його бачив телефон;
  застосунок сам іде на IP компʼютера з адреси Metro, порт 5173
  (`mobile/src/lib/config.ts`). `--host` відкриває dev-сервер усій
  мережі, а dev іде по http, тож лише у своїй мережі й з тестовим
  акаунтом. Брандмауер — лише порти 5173 і 8081 для приватних мереж
  (`mobile/README.md`), не весь node.exe.

## Що НЕ робити

- **Не запускати `shadcn-svelte add` з `--overwrite`.** Він мовчки
  перезаписує ВЖЕ НАЛАШТОВАНІ компоненти в `components/ui/**`: так
  зникали акцентний `variant="default"` у кнопки (той самий, що `primary`), розміри `xs`/`icon-sm`
  і `cursor-pointer`. Ставиш новий блок — постав, а потім
  `git checkout --` на всі змінені файли, крім справді нових. Перевіряти
  треба `git status`, а не вивід CLI: він показує «installed» і для того,
  що просто затер.
- Не чіпати `src/generated/prisma/` руками — тільки через `prisma migrate` /
  regen.
- Не міняти `Order.status` напряму, оминаючи `order-state-machine.ts`.
- Не писати перевірку ролі/сесії вручну в роуті — тільки через `guard.ts` /
  `guards.ts`.
- Не додавати категорійно-специфічні колонки в спільні моделі (`Job`,
  `Order`) — усе специфічне йде в `metadata: Json?` + контент-шар
  `src/lib/categories/`.
- Не показувати телефон клієнта чи майстра одне одному до вибору майстра
  (`Order` ще не створено) — це свідоме продуктове рішення з маніфесту
  («захист контактів до угоди», як у Uber). Дивись, як це вже реалізовано
  у `src/lib/server/profile.ts`, перед тим як міняти видимість полів.
- Не повертати персонажа «Zuna» — асистент говорить від імені платформи
  («Zunor»), без окремого імені/першої особи персонажа.
- Не писати текст асистента чи системні повідомлення казенною мовою («Ваш
  запит оброблюється») — тон має лишатися теплим і людяним, як описано в
  `MANIFESTO.md`.
- Не створювати новий `<Toaster>` чи новий кастомний toast-стор — тости
  тільки через `svelte-hot-french-toast`, підключений в кореневому
  `+layout.svelte`. Не імпортувати з `$lib/stores/toast-store.svelte.ts` чи
  `$lib/components/toast/*` — це мертвий легасі-код.
- Не додавати публічний `username`/сторінку для клієнта — навмисно є тільки
  у майстра (клієнт — не «вітрина», див. розділ «Профілі» маніфесту).
- **Не заводити локальний форматер часу.** «щойно / 5 хв тому / учора» живе
  в `$lib/utils/time` (`formatRelative`, `formatFull`). Ця функція вже була
  скопійована в шість місць і копії розійшлись: доба назад показувалась то
  «учора», то «1 дн», то «1 днів тому» на сусідніх екранах. Виняток один —
  календарний формат месенджера (сьогодні — час, цього тижня — день
  тижня): `components/chat/calendar-time.ts`, спільний для списку чатів і
  результатів пошуку в чаті. Це інша функція, а не копія.
- **Не писати `void проміс` для роботи після відповіді** (лист, Telegram,
  картка посилання, хвиля) — лише `background(проміс, 'мітка')` з
  `$lib/server/background`. На Vercel голий `void` обривається разом із
  функцією (розділ 2.1).
- **Не кликати `Notify.*` / `notify()` всередині транзакції.** Подія Pusher
  летить одразу після `create`, тож при відкаті у вкладці спалахне
  сповіщення про те, чого в базі немає. Сповіщаємо ПІСЛЯ коміту — саме тому
  `notify()` більше не приймає транзакційного клієнта.
- Не вигадувати `npm run lint` / `npm run test` — таких скриптів немає, є
  лише `npm run check`.
- Не коммітити `.env` чи реальні ключі, навіть у приклади/тести.
